# Execution semantics

This is the canonical contract for the implemented runtime. `crates/netplane` executes a Tower service root; `GraphBuilder` compiles one supported router topology into that root.

## Validation and publication

`GraphDraft` accepts a Tower service root, including one built with `ServiceBuilder` and layers. Its validation checks positive concurrency and buffer capacities and starts a Tower buffer worker. `GraphBuilder` accepts named Tower services, one request selector, declared route labels, an explicit fallback, and a router entry. Validation checks references, duplicate declarations, reachable backends, supported topology, and positive outer and backend capacities before starting any workers. Selector labels without a declared route use the fallback. Route and fallback declarations require a previously registered router; services and the entry can be declared in any order. The builder cannot prove application policy or interpret selector logic. The [live reconfiguration example](../../crates/netplane/examples/live_reconfiguration.rs) applies simulated authorization through ordinary Tower layers on each backend. That filter runs after route selection and backend readiness.

`Handle::execute()` admits a request and selects an immutable version synchronously when called, before its returned future is polled. `Netplane::publish()` atomically replaces a complete version using `ArcSwapOption`. An accepted request keeps its selected version through completion or future drop, so an old request can finish after a new composition is published. The Tower buffer worker polls readiness and calls the same owned service instance. Requests selected after publication use the new version.

## Capacity and cancellation

Each version has its own concurrency limit and bounded Tower buffer. Capacity is not shared across retained versions; a transition can therefore have work executing in both versions. The buffer bounds queued requests, while callers waiting for queue capacity remain pending. `RuntimeLimits::max_outstanding` bounds all accepted, unfinished request futures across versions and cloned handles, including unpolled futures and queue waiters. Admission happens synchronously at `Handle::execute()` or `try_execute()` invocation. At the limit, `try_execute()` returns `AdmissionError::AtCapacity` immediately; `execute()` returns a future containing that boxed error. Completion or future drop releases one slot. Publication does not reset the budget, and old-version requests keep their slots until completion or drop. Shutdown closure takes precedence over overload. This limit does not bound tasks spawned by services or request memory. The example routes requests between two independently bounded backend endpoints. Backend A initially withholds readiness while backend B remains ready, demonstrating independent backend progress when outer execution capacity is available. Its backend filters check a caller-provided Boolean after routing. Each selected backend endpoint polls readiness before dispatch. The router can report readiness while a selected backend is saturated, so backpressure appears while its execution future waits; outer execution slots can also cause head-of-line blocking. Independent backend readiness does not guarantee progress for a ready branch if other requests occupy every outer slot. This is only a simulated authorization decision, not identity authentication.

Dropping a queued request cancels its wait. Dropping a dispatched request future releases its global admission slot, but cancellation of the underlying call depends on the service. Thus `max_outstanding` bounds accepted Netplane request futures, not all service executions that may continue after cancellation. Netplane owns each Tower buffer worker and aborts it when the last owning endpoint and request future reference disappears, including when the worker is stuck in readiness.

## Shutdown

Calling `Netplane::shutdown(grace_period)` closes admission synchronously across handles, even before its returned future is polled. Publication is rejected from that point. Shutdown waits for accepted request futures to complete or be dropped, including futures never polled. A timeout reports the outstanding count and leaves admission closed and draining, so shutdown can be retried. A successful drain clears the active graph even if inactive handles remain. Shutdown cannot forcibly reclaim resources held by an uncooperative user-owned future or tasks spawned independently inside a service.

## Outside the current runtime

The runtime emits [structured tracing events](../observability.md) for admission, completion, cancellation, validation, publication, worker termination, and shutdown. Accepted-to-terminal duration includes any time before the first poll. A replaced version is released only after its last owner drops.

Arbitrary graph construction, policy validation, a reconfiguration control API, and HTTP integration remain future work.
