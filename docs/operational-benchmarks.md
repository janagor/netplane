# Operational benchmarks

The `operational_probe` example runs one in-memory workload per process and writes schema-versioned JSON (`schema_version` 2). It measures request completion latency with `Instant` and HDR histogram percentiles (3 significant figures, 1 ns through 60 s). Criterion remains the microbenchmark suite; its iteration distributions are not request latency percentiles.

## Run workloads

```bash
cargo run --release -p netplane --example operational_probe -- --profile smoke --scenario two-balanced --implementation netplane --output target/netplane.json
cargo run --release -p netplane --example operational_probe -- --profile smoke --scenario two-balanced --implementation tower --output target/tower.json
./scripts/bench-operational.sh standard target/bench-operational
```

Profiles supply defaults: `smoke` uses 2 clients, 0 seconds of warmup, and 1 second of measurement; `standard` uses 16, 3, and 15; `soak` uses 32, 10, and 120. Warmup reuses the same load driver with metrics collection disabled, then counters reset before the measurement interval. A short routing check (16 requests) runs before warmup. Override `--clients`, `--duration-secs`, `--seed`, admission and endpoint capacities as needed. Invalid values fail before graph construction. The current CLI supports `single`, `two-balanced`, `two-skewed` (95/5), `four-balanced`, `eight-balanced`, `publication`, and `retention`. `--slow-ms 5 --slow-in-flight 1` makes backend 1 slow while keeping other backends immediate.

The closed load model uses independent long-lived Tokio caller tasks. Each sends its next request after the previous one completes and records into a per-caller HDR histogram merged at the end. Open load uses `--load open --offered-rps N`; a single paced generator spawns up to `--generator-capacity` request tasks (twice the admission budget by default). `MissedTickBehavior::Skip` can reduce generated traffic when the generator falls behind, so reports include `scheduled_arrivals`, `generated_attempts`, `client_dropped`, and `offered_rps_achieved`. Netplane's synchronous admission failures are split into `rejected_at_capacity` and `admission_other_errors`. Use the same absolute offered rate for Tower and Netplane. The seeded request sequence is deterministic within a run; backend completion counts reveal the actual distribution. Calibrate sustainable rate with closed load before testing below, near, and above saturation.

The Tower fixture has one outer Tower buffer and concurrency limit, plus a selected backend buffer and concurrency limit with the same settings as the Netplane graph. Its router allocates the same label form and resolves it through a `BTreeMap`. A fixture-only semaphore enforces the same nonblocking global admission budget. Both use the same service behavior and seeded selector. The Tower fixture does not provide Netplane's publication, shutdown, or version retention semantics. Those scenarios therefore run only on Netplane. The older Criterion Tower fixture without global admission remains a diagnostic baseline and should not be labeled equivalent admission.

`publication` runs request traffic and controller `publish_if_current` calls concurrently. `--publications N` schedules attempts at `t = i * duration / N` for `i` in `0..N`, so the final publication is included under exact interval division. `--publications 0` is a no-reconfiguration baseline. Reports keep `requested_publications`, `successful_publications`, and `publications_after_window` (scheduled inside the window but skipped when wake or candidate construction finishes after `end`). Candidate construction and publication have separate percentile fields. The request response verifies the selected backend; publication generation may vary by arrival time. The resource scenario publishes graphs with counted, noncloned service instances. `--retention-mode paced`, `burst-short`, and `burst-long` retain unpolled old requests for one, ten, or all publications, then drop them. Retention reports `cancelled_requests` and `publication_rate`; `throughput_rps` is null because no requests complete. For `burst-long`, set `--max-outstanding` to at least the publication count. A bounded cleanup wait asserts zero live resources after shutdown. These counts refer to owned service instances, not controller history entries. `peak_rss_bytes` reads Linux `VmHWM`; it is null elsewhere. Run each resource scenario in a fresh process because `VmHWM` is process-lifetime high water.

Each JSON result records attempted, admitted, completed, completions inside and after the measurement window, drain cancellations, runtime errors, admission rejections, client drops, backend counts, throughput from in-window completions, latency percentiles for every request admitted during the window (including those that finish during the bounded drain), `latency_samples` / `missing_latency_samples`, `measurement_complete`, publication timings, open-loop `nominal_arrivals` / observed tick `scheduled_arrivals` / `generated_attempts`, resource counts, and environment details. Closed-loop drain waits until `measurement_end + 5s`. Open-loop admission requires `Instant::now() < measurement_end` at the call site. Open-loop latency uses a fixed set of histogram shards; elapsed time is captured before any instrumentation lock. Comparison scripts require schema version 2 only, reject incomplete runs (`drain_cancelled`, `admission_other_errors`, missing latency samples, or `measurement_complete=false`), and use nanoseconds to avoid rounding away fast-path differences. Throughput uses completions within the configured measurement interval; total completed includes drain. Unsupported metrics are null. The runner validates counter relationships before writing JSON. `dependency_fingerprint` hashes the resolved local `Cargo.lock` if present; save the lockfile with controlled results because this library workspace ignores it. The October 2026 exploratory one-second baseline remains historical and is not directly comparable with corrected schema-v2 runs.

## Compare revisions

```bash
./scripts/bench-compare.sh --base main --head HEAD --profile standard --scenario four-balanced --runs 5 --output target/bench-comparison
```

The script resolves exact SHAs, builds isolated worktrees in release mode, saves each generated `Cargo.lock`, and refuses strict pairing if the lockfiles differ. Pass `--scenario` and optional trailing probe arguments after `--`. It requires the runner in both revisions; the parent of the first PR introducing this runner must instead be compared with Criterion benchmarks present in both revisions. It warms each binary, alternates base/head order across at least five pairs, and writes individual JSON files plus `comparison.json` and `comparison.txt`. The report validates schema version, matching scenario and config, compiler/target/dependency fingerprint, measured duration, zero runtime errors, and counter invariants before summarizing. It gives run-level medians and paired change ranges; it makes no automatic regression verdict. A performance decision should consider host load, CPU governor, thermal state, compiler, target, and repeated variation. A percentage change in p99 from a single pair is not sufficient evidence.

## HTTP gateway

`./scripts/bench-http.sh target/bench-http 1000 16 5 1000` builds the policy gateway, refuses to start if ports 3000 or 3001 are already bound, records the installed `oha` version, and saves JSON for stable-only, canary-only, mixed, and reconfiguration-during-traffic runs. The script requires `oha`, `curl`, `openssl`, and Python 3. Controlled keys are `bench-0` (stable), `bench-2` (canary), and `bench-4` (stable at 25% canary, canary at 50%). Mixed traffic runs four simultaneous rate-limited groups over a shared duration with an explicit 75/25 split. The reconfiguration workload verifies `bench-4` routes to stable before publication and canary afterward, and checks the administrative reconfigure response plus status policy. HTTP results include transport, body handling, OS network stack, and client costs, so they should not be combined with in-memory results.

## Limits

No shared CI performance threshold is used. CI compiles the runner and checks a short JSON smoke run for correctness. Request latency includes queueing and scheduling. HDR histograms keep a fixed memory footprint; long soaks no longer store one sample vector entry per completion. `VmHWM` measures the benchmark process, including the runner, and is not a Netplane allocation count. Publication rate is approximate because candidate building and Tokio scheduling take time. The benchmark does not guarantee fairness between fast and slow backends; outer capacity can cause head-of-line blocking.
